# Notes on the Implementation

## 1. What NVIDIA Auto Ontology Does

NVIDIA Auto Ontology is an open-source library (Apache 2.0, [github.com/NVIDIA/auto-ontology](https://github.com/NVIDIA/auto-ontology)).
It runs as a local Docker stack with four services:

| Service | Port | Role |
|---------|------|------|
| Frontend (Next.js) | 3000 | Web UI: data catalogue, chat, settings |
| Backend (FastAPI) | 3001 | NL-to-SQL, semantic compilation API |
| Ingestion worker (FastAPI) | 3002 | Writes embeddings to Postgres |
| Postgres + pgvector | 5432 | Stores the app state, catalogue, and vector index |

You connect it to a database, trigger **Semantic Compilation** (the library calls
the NVIDIA LLM to propose business entity names for each table and attribute meanings
for each column), and export the result as a YAML file containing a `data_layer`
(raw schema with stable UUIDs) and a `semantic_layer` (LLM-proposed terms).

**What it produced for Olist** (commit `fc43a826`):
- 9 table-level terms (one per table, named after the table).
- Placeholder (empty) descriptions for all entities and attributes.
- 0 foreign-key relationships — expected; Olist has no FK constraints.

The stable UUID mapping is Auto Ontology's main structural contribution: it
decouples the ontology from raw table names, so a renamed table still links to the
correct entity. The description enrichment and relationship discovery are this
pipeline's own additions.

## 2. What I Changed or Added (My Work)

| Addition | Why |
|----------|-----|
| **Generic PK inference** (`db_inspector.py`) | Auto Ontology assumes keys exist. The tool infers them from uniqueness and name patterns. Composite keys and the no-key case (geolocation) are both handled. |
| **Relationship discovery** (`relationship_finder.py`) | Auto Ontology found 0 relationships. This module infers foreign keys and lookup links using name similarity + value containment, with confidence scores. |
| **LLM validation layer** (`llm_client.py` + `validator.py`) | Auto Ontology has no built-in guard against hallucinated column names. Every LLM claim is cross-checked against the real schema before it is accepted. |
| **Article-correct sentence generation** (`llm_client.py`) | Added `_article()` to pick "A" vs "An" in code; cardinality is passed to the LLM prompt so it uses the right quantifier; a regex check in `check()` rejects any sentence that still has "A Order" etc. |
| **Data-driven surrogate-key notes** (`normalizer.py`) | `_surrogate_key_notes()` scans one-to-one relationships for sibling columns with "unique"/"uuid" in their name and fewer distinct values than the row count — generating a note from the data rather than typing it. |
| **Schema-only fallback** (`normalizer.py` + `main.py`) | If Auto Ontology cannot be run against an unseen database, the pipeline continues using the inferred schema structure. |
| **End-to-end orchestration** (`main.py`) | Ties all five steps into one `--db` command with a clear exit code. |
| **Disk cache** (`.llm_cache/`) | LLM calls are SHA-256 keyed and cached, so the pipeline is reproducible without an API key when the cache is present. |

## 3. Where the Tool Got Things Right on Olist

- **Clear entity recognition**: correctly identified 9 business entities.
- **Composite key**: correctly inferred `(order_id, order_item_id)` as the composite
  primary key for `olist_order_items_dataset`.
- **No-key table**: `olist_geolocation_dataset` correctly gets no primary key
  (`geolocation_zip_code_prefix` is not unique).
- **All 7 real FK relationships found** with zero false FK links between child tables.
- **Attribute descriptions**: 52/52 attributes have real plain-English meanings;
  validation confirmed zero templated or blank meanings.

## 4. Where It Got Things Wrong / Where Auto Ontology Falls Short on Olist

| Issue | Detail |
|-------|--------|
| **`customer_id` is a per-order surrogate** | Each row in `olist_orders_dataset` has a distinct `customer_id`, making the Order → Customer link appear 1-to-1. The cardinality is set to `one-to-one` (matching the data) and the sentence says "An Order belongs to one Customer." The `data_notes` field (generated by `_surrogate_key_notes()` from the data, not typed by hand) records that `customer_unique_id` has 96,096 distinct values vs 99,441 rows. |
| **Auto Ontology empty descriptions** | The raw export had empty descriptions for all entities and attributes. The NVIDIA LLM step in `llm_client.py` fills them in. Auto Ontology's value here is the UUID-based entity mapping. |
| **Geolocation redundancy** | Three lookup links were found: customer zip → geolocation zip, customer city → geolocation city, seller zip → geolocation zip. The city link is partially redundant with the zip link; both are valid but a human reviewer might drop the city one. |
| **Validation is partly circular** | The validator re-runs the same SQL containment query used during relationship discovery. This confirms consistency but cannot detect a case where both steps are wrong for the same underlying reason. |
| **Portuguese category names** | The LLM described `product_category_name` values as-is. A translation step would improve this. |

## 5. What I Would Improve Next

1. **Gold-standard test**: add a second database (e.g. Northwind or AdventureWorks)
   with known FKs and validate that the tool finds them all with no false positives.
2. **Cardinality from unique-id analysis**: extend `_surrogate_key_notes()` to flag
   the relationship itself as "logically many-to-one" when a surrogate key is detected.
3. **Human-in-the-loop CLI**: a simple `python review.py` to accept, reject, or edit
   entity descriptions and relationship sentences before the final YAML is written.
4. **Translation layer**: a lightweight dictionary or dedicated LLM call for
   Portuguese category names.
